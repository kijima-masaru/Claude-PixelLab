# パレット分析 — 参考資料から何を採り、何を捨てたか

`projects/iwato/refs/` の参考資料14点（ゲーム画面9点＋実写5点）を測定し、
そこから64色パレットを設計した記録。

**参考画像は API に一切送っていない。** 見て分析し、言語化し、独自の色を
構築するためだけに使った。色そのものは著作権の対象外であり、抽出は問題ないが、
**画像を生成の入力にはしない**（`tools/lib/guard.py` がコードで担保している）。

---

## 2. 測定 — 何を採ったか

中央のプレイ領域のみを対象とした（周辺のビネットと UI を除外）。
光部＝輝度上位12%、影部＝輝度下位30%。

| 指標 | ゲーム画面9点 | 実写5点 | **採用値** |
| --- | ---: | ---: | ---: |
| 明度比（光÷影） | 8.4 | 39.1 | **8:1** |
| 光と影の色相差 | 32度 | 28度 | **30〜40度** |
| 影の彩度 ÷ 光の彩度 | 2.27 | 1.11 | **1.8** |
| 光部の平均彩度 | 0.37 | 0.29 | 低い |
| 影部の平均彩度 | 0.65 | 0.41 | **光より高い** |
| 暗部の階調段数 | 10 | 3 | **10段前後** |

### 採った構造 ①：影が色を持つ

**光が当たった面は彩度が低く（白へ抜ける）、影が彩度を持つ。**
ゲーム画面では影の彩度が光の 2.27倍、実写を含めても 1.8倍。

これは直感と逆だが、意味は明快である。光源そのものは高彩度だが、
**光を受けた面は白へ飽和して彩度を失う**。一方で影は環境光の色に染まる。

→ **藍も墨も「濃い灰色」ではなく「濃い色」でなければならない。**

パレットへの反映：`indigo` の暗端を彩度 0.60 と高く取り、`ink`（無彩色）は
9色に抑えた。**暗部を無彩色で作らない**という設計判断の根拠がこれである。

### 採った構造 ②：3つの照明レジーム

実写を分類したところ、**光と影の色相関係が場面によって反転する**ことが分かった。

| レジーム | 光の色相 | 影の色相 | 色相差 | 該当資料 | 該当フィールド |
| --- | --- | --- | ---: | --- | --- |
| **A** 暖色光 × 寒色影 | 45〜48度 | 210〜220度 | **162〜175度** | コンビニ、商店街 | F01, F05, F12, F13 |
| **B** 寒色光 × 寒色影 | 194〜206度 | 220度 | **14〜26度** | 自販機、高架下 | F03, F06 |
| **C** 自然光 暖 × 暖影 | 52度 | 80度 | 28度 | 杉林、ゲーム9点 | F04, F07, F08, F16 |

**これが本パレット設計の最大の焦点である。**

レジーム A では色相差が最大になり、B では**色相差がほぼ消える**。
Bでは明度と彩度だけで光と影を分離しなければならない。

片方に寄せた設計をすると、もう片方のフィールドが破綻する。そこで：

- **地の色は52色すべて褪せさせ、色相差に頼らない構造**にした。
  どのレジームでも明度段で形が読める
- **光源色12色を独立させ、時間帯置換の対象から外した**。
  レジームAの暖色光（`sodium` `bulb`）とレジームBの寒色光（`fluoro` `vending`）を
  両方パレットに持ち、フィールドごとに使い分ける
- 影は全系統で**色相 200〜268度側に暗端を寄せた**（実写の影の色相中央値 220度）

### 採った構造 ③：暗端は藍へ、明端は素材の色へ

各ランプの**暗端の色相を藍寄り（198〜268度）、明端を素材固有の色相**にした。

```
green : 198度（暗い青緑） → 104度（黄緑）
earth : 356度（陰った赤褐色） → 36度（黄土）
concrete : 216度 → 204度
```

低照度では色が褪せて環境光の色（夜は青）へ寄る、という現実の挙動に一致する。
**そしてこれが時間帯置換を成立させている**（後述）。

## 3. 捨てたもの

| 捨てたもの | 理由 |
| --- | --- |
| **参考元の色相そのもの** | 暖色寄りで明るく、宝石箱のような華やかさがある。本作は日本の8月の湿った暗い田舎町であり、そのまま持ち込むと作品と喧嘩する。学んだのは「暖色の光 対 寒色の影」という**構造**だけ |
| **実写の暗部の階調** | 実写の暗部は真っ黒に潰れている（中央値3段、最小1段）。そのまま模倣するとプレイヤーが歩けない |
| **ゲーム画面の明度比 24〜37倍** | 炎に照らされた2点は極端で、暗部が3〜5段しかない。外れ値として除外し、夜の集落群の 5.4〜12.2倍を採った |
| **高彩度の面** | 参考元は高彩度画素率が最大93%。本作は光源12色のみに彩度を許す |
| **斜め見下ろしの立体表現** | 本作は真上見下ろし。参考元の視点は採らない |
| **被写界深度・ティルトシフト** | 32pxタイルでは表現できず、またそれに頼る画面設計をしない |
| **予備の色枠** | 当初3色を予備にしたが廃止した。パレットは spec から生成されるため、必要になればランプの段数を1つ増やせば済む。**意味のない色で枠を埋めるより全64色に役割を持たせるほうがよい** |

## 4. 段数の根拠

**実写のほうが階調が連続的だが、暗部については実写のほうが段数が少ない。**
これは重要な発見で、素朴な想定と逆である。

| 資料 | 暗部（下位30%）の識別可能段数 |
| --- | ---: |
| ゲーム画面（夜の集落群） | 7〜14段 |
| ゲーム画面（炎の2点） | 3〜5段 |
| **実写5点** | **1〜6段（中央値3）** |

実写の暗部が潰れているのは**カメラのダイナミックレンジの限界**であって、
人間が現場で見ている階調ではない。一方ゲーム画面の暗部階調は
**「ゲームとして成立させるために作家が意図的に置いた段数」**である。

したがって **段数の根拠は実写ではなくゲーム画面群を採る。**

### 決定した段数と、その導出

1. **下限**：ゲーム画面の夜の集落群が暗部に 7〜14段（中央値10）を持つ。
   これが「暗いが歩ける」ための実績値。→ **暗部に10段前後**
2. **上限**：64色という制約。光源12色を引くと地の色は52色。
   7系統に配分すると1系統あたり平均7.4段
3. **識別可能性**：隣接段の明度差が 3.0（0-100スケール）を下回ると
   32pxでは潰れて見える。`build_palette.py` が毎回検査し、
   下回れば生成を失敗させる

結果：**`ink` 9段 / `concrete` 8 / `indigo` 8 / `green` 8 / `earth` 9 /
`violet` 6 / `skin` 4 = 52段。**

明度配分には gamma 1.2〜1.5 を掛け、**暗部に段を厚く割いた**。
本作は暗所が主戦場であり、明部の段数は少なくてよい。

`ink` `concrete` `indigo` の3系統が暗部で重なるため、
**最暗部の実効段数は10段以上を確保できている**（要件を満たす）。

## 5. 時間帯置換テーブルの検証

**485点全体に影響する箇所であるため、設計段階で機械的に検証した。**

### 成立させるための構造

置換を**「色A → 色B」ではなく「系統と段のシフト」**として定義した。
これにより**置換先が必ずパレット内に存在する**ことが保証される。
色を直接指定する方式だと、指定先がパレットに無い事態が起きる。

さらに、各ランプの暗端をあらかじめ藍寄りにしてあるため、
**別系統へ写像しなくても段を下げるだけで夜になる。**

### 検証結果

| 時間帯 | 地の色52色のうち識別できる色数 | 潰れ | 判定 |
| --- | ---: | ---: | --- |
| 昼 | 52 | 0 | 基準 |
| 朝 | 47 | 5 | 良 |
| 夕 | 49 | 3 | 良 |
| **夜** | **38** | **14** | **可** |

夜の潰れ14は、各ランプの最暗2段（`earth` は3段）が端で丸められるために起きる。
**深い闇で全てが黒へ収束するのは物理的に正しい。**
38色残れば、夜景でも草・土・道路・コンクリートがそれぞれ別の色を保つ。

### 設計途中で発見し、修正した破綻

**当初の設計では夜に 49色中28色が潰れた（識別21色）。**
緑・土・コンクリートをすべて藍ランプへ写像していたためで、
これでは**夜景で草も土も道路も同じ色になる**。プレイヤーが地形を
判別できず、485点の素材差が夜に消える。

修正：**藍への集約をやめ、各ランプの暗端そのものを藍寄りに設計し直した。**
これにより素材の区別を保ったまま夜にできる（潰れ 28 → 14）。

もう1点、`earth` だけ夜のシフトを -3 にした。**暖色は同じ明度でも
知覚的に明るく見えるため**、-2 では夜景で土だけが浮いた（スウォッチで確認）。

### 検証は自動化してある

```bash
python tools/build_palette.py --project iwato --verify-only
```

- 総色数が64ちょうどか
- 重複した色が無いか（1色でも重複すれば実質的に色数が減る）
- 置換先が全てパレット内に存在するか
- 置換で潰れる色数
- 隣接段の明度差が32pxで識別できるか

**spec を編集するたびにこれが走る。** 破綻したまま気づかない事態を防ぐ。

## 6. 前回の測定値からの変化

実写5点を加えて再測定した結果、**1項目が変わった。**

| 指標 | 前回（ゲーム9点のみ） | 今回（14点） | 変化 |
| --- | ---: | ---: | --- |
| 明度比 | 8:1 | 8:1 | 変化なし |
| 色相差 | 30〜40度 | 30〜40度 | 変化なし |
| **影の彩度 ÷ 光の彩度** | **2.5** | **1.8** | **下方修正** |
| 「影が色を持つ」 | 成立 | 成立 | 変化なし |

実写では影の彩度比が 0.49〜3.37 と大きくばらつく。とくに
**夜のコンビニの駐車場は 0.49**（影のほうが彩度が低い）。
広いアスファルトの闇は無彩色に近づく。

→ パレットへの反映：**暗部に「無彩色寄りの墨（`ink`）」と
「彩度のある藍（`indigo`）」の両方を用意した。** 片方だけだと、
アスファルトの闇と高架下の闇の両方は表現できない。

前回の 2.5倍は**ゲーム画面に寄りすぎた値**だった。

## 7. 未解決の事項

- **④ 月光のみの屋外の資料が無い。** `violet` と `moon` で設計上は用意したが、
  実際に F04 / F09 / F14 / F15 の夜を作る段階で不足が出る可能性がある。
  その時点で追加撮影を依頼する
- **32px の実素材で検証していない。** スウォッチ上では成立しているが、
  実際のタイルで隣接段が識別できるかは F06 パイロットで確認する
- **`accent` の使用面積の上限が未定。** 「極小面積にのみ」としているが、
  具体的な画素数の目安は実素材を見てから決める
- **`skin` 4段はキャラクター用ではない。** UI とアイコンで手や顔を描く場合の
  最小限。キャラクター素材は本リポジトリの対象外である
